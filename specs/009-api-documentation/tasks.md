## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: No dependencies — start immediately
- **Foundational (Phase 2)**: Depends on Setup — BLOCKS all user stories
- **User Story 1 (Phase 3)**: Depends on Foundational only
- **User Story 2 (Phase 4)**: Depends on Foundational AND on User Story 1's route mount (T011) — Swagger UI has nothing to render until a contract and route exist
- **User Story 3 (Phase 5)**: Depends on Foundational AND on User Story 1's generated artifact (T010) existing to diff against
- **Polish (Phase 6)**: Depends on all three user stories being complete

### Within Each User Story

- Tests written and failing before implementation (T007/T008 before T009-T012; T014 before T015-T016)
- Annotate → regenerate → mount route → verify tests green

### Parallel Opportunities

- T002 and T003 (Phase 1) — different files
- T007 and T008 can be written together (same test file, additive) but are listed sequentially since they share a file
- T013, T017, T021 — documentation tasks in different files than their story's implementation tasks
- T022, T023, T025 (Phase 6) — different files

## Implementation Strategy

### MVP First (User Stories 1 + 2 — both P1)

1. Complete Phase 1: Setup
2. Complete Phase 2: Foundational (blocks everything)
3. Complete Phase 3: User Story 1 (contract generation)
4. Complete Phase 4: User Story 2 (interactive UI) — depends on US1's route mount
5. **STOP and VALIDATE**: run `quickstart.md` Scenarios 1, 2, 4 independently
6. Deploy/demo if ready — this is the deployable MVP slice

### Incremental Delivery

1. Setup + Foundational → toolchain ready, empty contract committed
2. User Story 1 → contract auto-generates from code (US1 validated)
3. User Story 2 → contract browsable + "Try it out" works (US2 validated, MVP complete)
4. User Story 3 → CI gate prevents future drift (US3 validated)
5. Polish → docs cross-references, full quickstart re-run, coverage check
